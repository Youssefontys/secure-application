# Trust boundaries

| ID | Tussen | Wat verandert er over deze grens | Sinds |
|----|--------|----------------------------------|-------|
| B-01 | Internet/gebruiker (C-01) en webapplicatie (C-02) | Alles wat van de browser komt is onbetrouwbaar: formuliervelden, cookies, headers, de URL (ook `note_id`). De app moet het zelf valideren. Op de grens staan een lengtegrens op titel en notitie (MIT-04), een lengte-eis op nieuwe wachtwoorden (MIT-13), een eigenaarscontrole op elke notitie (MIT-15), het huidige wachtwoord en een code uit de app bij wachtwoord wijzigen en account verwijderen (MIT-16) en limieten op foute wachtwoorden (MIT-10), foute codes (MIT-06) en foute herstelcodes (MIT-11, MIT-14). Sinds Week 7 ook: een CSRF-token op elke POST (MIT-20), beveiligingsheaders (MIT-21), een gebruikersnaam van 3 tot 20 letters, cijfers en _, hoogstens 16 KiB per verzoek en alleen een POST die iets uitvoert (MIT-22), elke route standaard dicht (MIT-24) en een korte foutmelding zonder details (MIT-25). Daarna: geen pagina in de cache van de browser (MIT-28), een sessie van hooguit 8 uur (MIT-29), en een limiet op registreren per adres en op notities per account (MIT-30). Geen TLS lokaal; op Azure HTTPS van het platform, en HTTP gaat met een 301 naar HTTPS (gemeten op 18-10-2026). De TLS-instellingen van het platform zijn getoetst aan de richtlijnen van het NCSC: nergens Onvoldoende (MIT-40, T-113). | baseline |
| B-02 | Webapplicatie (C-02) en database (C-03) | De app vertrouwt de database. De database vertrouwt de app maar beperkt: de app logt in als `notes_app` en mag alleen lezen en schrijven in de eigen tabellen (MIT-27). Een gecompromitteerde app kan dus alle rijen lezen en wijzigen, maar geen tabellen weggooien, geen rollen maken en niets via `COPY`. Andersom niet helemaal meer: de sleutel van het TOTP-geheim (A-09) blijft in C-02, dus wie alleen de database heeft, kan het geheim en de notities niet lezen (MIT-17, MIT-18), en vindt van wachtwoorden alleen een hash (MIT-19). Op Azure heeft de database geen openbaar adres: alleen het eigen netwerk komt erbij, en de verbinding is TLS 1.3 met `verify-full` (F-03). | baseline |
| B-03 | Database (C-03) en host (C-04) | Wie de host of het volume leest, leest de data. Lokaal geen versleuteling op schijfniveau; op kolomniveau het TOTP-geheim en de notities (MIT-17, MIT-18). Op Azure is de host van Microsoft: de schijf is versleuteld met een sleutel van Azure, en wie bij Microsoft bij de host kan, valt buiten wat wij kunnen tegenhouden; de kolomversleuteling blijft gelden. | baseline |
| B-04 | GitHub (C-06) en Azure (C-02) | Wat op Azure draait, komt uit de pipeline: wie naar `main` kan pushen, of een action of het token van de run kan misbruiken, bepaalt de code van de app (MC-30). Op de grens: alleen een push naar `main` publiceert (een pull request wordt alleen gebouwd en gescand, B-06), een image met een bekend lek gaat niet door (MIT-35), het token heeft alleen `packages: write` en `contents: read`, en checkout staat vast op een commit (MIT-34). Uitrollen gaat nog met de hand (`deployment.py azure`), met een plan dat op yes wacht. | 19a34dd |
| B-05 | De beheerder (C-10) en Azure | Alles op Azure wordt gemaakt en gewijzigd vanaf de pc van de beheerder, met zijn Entra-login (A-16, Owner op de subscription). Wie die login of een geldige `az login`-sessie op die pc heeft, beheerst alles: resources, rollen en dus ook de geheimen. Op de grens: de tenant vraagt een tweede stap bij het inloggen, Terraform wacht op `yes`, de geheimen gaan write-only naar Key Vault en staan niet in het plan of de state, de state alleen via Entra ID zonder accountsleutels (C-09, MIT-38), en voor de geheimen in de vaults geeft Terraform de beheerder alleen Key Vault Secrets Officer (AZ-12). Restrisico: als Owner kan de beheerder zichzelf elke rol geven (MC-31). | 75c9967 |
| B-06 | Een pull request (C-11) en de pipeline (C-06) | De code van een pull request is onbetrouwbaar, ook de workflow en de Dockerfile die erin staan: bij een pull request draait GitHub de workflow uit die pull request, en `docker build` voert de `RUN`-regels uit. Op de grens: de job `check` krijgt alleen `contents: read`, vanuit een fork geeft GitHub sowieso alleen leesrechten en geen secrets, en er wordt niets gepubliceerd (MIT-39). Een ruleset laat alleen een pull request met een geslaagde check op `main` komen (AZ-16). Restrisico: een pull request die de check zelf aanpast, of een verklaring in de VEX (A-18) zet, kan die groen maken; alleen wie mergt, ziet dat in de wijzigingen (MC-30). | bc6c669 |
